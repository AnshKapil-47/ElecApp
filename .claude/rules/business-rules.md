# Business rules (always loaded)

## Clients

- **Web app:** OWNER and SUBOWNER only.
- **Mobile app:** AGENT, CUSTOMER, SUBUSER. Each app user has one registered phone (device key).
- Enforced in the DB: `user_session` WEB ⇔ OWNER/SUBOWNER; `user_device` only for AGENT/CUSTOMER/SUBUSER.

## Roles and who creates whom

```text
OWNER ─┬─ SUBOWNER (only Owner creates)
       └─ AGENT    (Owner or Subowner creates)
              └─ CUSTOMER ACCOUNT (Agent, Owner or Subowner creates; owned by one Agent for selling)
                     ├─ CUSTOMER        (exactly one primary login, activates once)
                     └─ SUBUSER         (only the Customer creates)
```

- `customer_account.created_by_user_id` = permanent provenance. `owning_agent_user_id` = the only Agent who may sell to that Customer. Only the Owner reassigns it (e.g. when an Agent leaves). Owner/Subowner-created Customers have no owning Agent until the Owner assigns one.

## Election types (lenses) and fields

- 8 types: LOK_SABHA, VIDHAN_SABHA, NAGAR_NIGAM, NAGAR_PALIKA, NAGAR_PARISHAD, ZILLA_PANCHAYAT, PANCHAYAT_SAMITI, PANCHAYAT.
- The Excel sheet is the rule: **skin (orange) cell = FILTER** (defines the area the Agent sells), **green cell = DISPLAY** (what the Customer sees; filters are also shown), white = not used. Stored in `election_type_field`; generated by `tools/seed/gen_seed.py`. Never hand-edit the CSV.
- FILTER sets: Lok Sabha = state, pc_no, ac_no · Vidhan Sabha = state, ac_no · Nagar Nigam = state, district, municipal_name_nagar_nigam_en, nagar_nigam_ward_no · Nagar Palika = state, district, nagar_palika_ward_no · Nagar Parishad = state, district, nagar_parishad_ward_no · Zilla Panchayat = state, district, zilla_parishad_name_ward_no · Panchayat Samiti = state, district, panchayat_samiti_name_ward_no · Panchayat = state, district, panchayat_no.
- Booth column: `part_no` for Lok/Vidhan Sabha, `booth_no` for local bodies (`election_type.booth_column`).
- Ambiguity guard: for Palika, Parishad, Samiti, Panchayat, if a sold area's voters carry more than one distinct `election_type.guard_column` value, refuse the line with `AMBIGUOUS_AREA`.
- `_mt` = Mother Tongue (regional language), `_en` = English.

## Data tiers

- **MASTER:** the current election only. Imported in bulk before the election. `delete_after` = import + 60 days. A MASTER entitlement can never run past it.
- **LONG_TERM:** when a Customer needs more than ~2 months, the Agent phones the Owner; the Owner imports that area as LONG_TERM. Kept until the latest entitlement on it ends + 30 days.
- One area exists at most once per tier among IMPORTED datasets (overlap probe on `source_record_key_hash`). Corrections are imported as a new dataset that **supersedes** the old one; existing entitlements finish on the old data.

## Sale (Agent, in the mobile app)

1. Customer (must be ACTIVE, caller must be its owning Agent) → 2. election type → 3. **tier first** → 4. one or more areas (all FILTER values, cascading dropdowns from IMPORTED datasets of that tier) → 5. duration per line (≥1 DAY/WEEK/MONTH) → 6. submit with an idempotency key.
- Backend resolves exactly one dataset per line (zero → "area not available for this tier"; two → error to the Agent + audit row). Agent never sees dataset ids.
- `valid_from` = max(sale time, end of the Customer's current ACTIVE entitlement for that lens+tier+area) → renewals are back-to-back. `valid_until` = valid_from + duration (Asia/Kolkata calendar math; MONTH clamps to month end).
- One transaction writes `agent_sale`, `agent_sale_line` (snapshots) and one `entitlement` per line.
- Void: Owner only → sale VOIDED (who/when/why) + its entitlements REVOKED + Customer `mobile_access_policy_version` + 1.
- Direct grant (Owner/Subowner): same logic, `source = DIRECT`, no sale rows, never in Agent reports.

## Customer lifecycle

Provision (name, org, phone E.164 unique, email) → 10-char activation code (72 h, 5 attempts, re-issuable) → activation in the app (phone + code → set password) → login → dashboard of entitlements (type, area label, validity, remaining time; expired shown as expired; future ones "starts on") → voter list (server pagination ≤ 100) → Print Slip / Details / Family → turnout marking → statistics. Account ACTIVE or SUSPENDED; suspension ends all sessions of the Customer and its Subusers.

## Booths and Subusers

- Max 2 active assignments per Subuser at any moment (slots 1/2, DB exclusion), each ≤ 7 days and never past the entitlement. No limit per booth. Booth value must exist inside the entitlement's area.

## Turnout

- One row per (dataset, Customer, voter) = "voted". First valid mark wins; repeats are confirmations (`ON CONFLICT DO NOTHING`). Server time. Only the Customer, online, may unmark or reset an area. Never record how anyone voted.

## Phone-only operations (no in-app requests, no notifications)

Customer wants data → phones Agent → Agent sells. Needs > 2 months → Agent phones Owner → Owner imports LONG_TERM. Wants mobile numbers → Agent phones Owner → Owner switches it on per entitlement. Mistaken sale → Owner voids. Lost phone / forgotten password → Owner revokes device, ends sessions, resets password. Expired code → Agent/Owner/Subowner re-issues.

## Reports (quantity only, one reporting service)

Owner: per Agent and period — sales, sale lines, Customers acquired, type, state, district, scope label, times each scope sold, distinct scopes `(election_type, criteria_hash)`, voided lines separately. Agent: same, own only. Customer: turnout by area and booth. Subuser: own booths. Subowner: no sales reports.
